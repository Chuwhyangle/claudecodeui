**code-shape gate 是最大的精度杠杆。** 它要求光标前的片段带分隔符、数字、全大写缩写，
或 ≥5 字符的混合大小写标识符；`server`、`chip`、`task`、`architecture` 这类普通英文名词不再触发。
代价是 3 个纯小写 token 的 top-1（`architecture` → 模块路径、`context` → 路径、`withdraw` → 标识符），
换掉约 43 个误报回合。

**软真值（code-line/heading 的逐字复制）** 在 979 个回合里只有 1 个，且排名第 2。
这不证明标题/段落没用——它证明它们**不是“复述补全”的surface**，而是语义指代的 surface；
后者需要人工标注，逐字复制口径看不见。

## 6. 未命中的 10 个回合

- **语义 / 分词差异**：`ARCHITECTURE_TAB` 被写成 “architecture tab”（×2）、`server_vad` 写成 “server VAD”。
  需要按 `_` / `-` / camel 拆词后再匹配，属于 v2。
- **纯小写 token 被 gate 拦掉**：`architecture` → `src/modules/architecture`、`context` → `honors.prompt/context`、

- **本来就不是补全机会**：`multi-lang`、`function_call` 是比用户已输入 token 更短的片段；
  `ArchGuard` 与 `.archguard` 规范化后相等，按“回声”丢弃。
- **真值口径 artifact**：`live-voice-enter` 是靠去标点后的跨词匹配进来的，用户并没有逐字打这个标识符。

## 7. 结论与 v1 建议

> **§10 的人工标注修正了本节的重要性判断。** token 补全本身是精确的，但它只服务
> 14 个真人 `specific` 引用里的 1 个；真正会用的是“把被指到的段落/条目插进来”。
> 先读 §10，再把本节当作**第二层**（用户确实在打代码 token 时）的建议。

1. **v1 只显示 code-shaped 补全**：path + identifier；`minQueryChars=4`、`maxCandidates=3`、
   basename key 开启、120 ms 去抖。
2. **展示短列表，不猜单个**：45% 的命中回合有 2–3 个候选；`Tab` 接受、`↑/↓` 选择、`Esc` 消隐，
   **`Enter` 始终是发送**。接受走现有 `acceptChip` 的“填入 + 光标 + Ctrl+Z”，绝不自动发送。
3. **标题/段落继续提取、暂不作为补全显示**：等语义指代的人工标注实验，而不是逐字复制口径。
4. **numbered items 停用是独立决策**：新旧 surface 只重叠 10 个回合；停用丢掉 52 个序号指代回合。
   现有 UI 未改；真停用的改动点是 `ChatComposer.tsx:955-957` 与 `ChatInterface.tsx:827-841`。
5. **下一步**：60 对人工标注（强/软/无目标 + “这个建议帮到你了吗”）评价语义层；
   接线获准后再做 shadow 日志（只记录不显示）与交互式 A/B。

## 8. 限制

- 回放的是**最终文本的每个前缀**，不是真实击键；没有 IME 上屏、退格、改写、光标移动。
- 没有接受行为数据；这里的“可用性”是精度/召回/出现时机/候选数的代理，不是用户研究。
- 强真值只认 path/identifier 的逐字复制；语义指代被算进误报分母，所以 **2.1% 是误报上界**。
- 一个用户、一个项目、14 天；结论用于设计与回归检测，不做统计显著性宣传。
- 全部 offline。没有改动 composer、没有上线、没有遥测。

### 10.4 修正后的判断

1. **token 补全（reference targets）是精确的，但不是主价值。** 它只覆盖 1/14 个真人
   specific 引用；8/9 的情况下人只是提到那个 token，并不会打它的前缀。
2. **真正的需求是“插入被指到的 span”。** 13/14 的 specific 指向段落/标题，
   14/14 说会用；前缀匹配对它们 0 覆盖。
3. **旧 numbered preview 的形态其实更接近人的说法**（numbered 层 7/10 会用），
   它没人用是因为**只读**。停用只读预览是对的；把预览行变成“可接受的插入”比删掉更有依据。
4. **下一步的离线实验应换成 deictic → span**（§11 已给出新的语料与基线）：
   输入光标前的短句，候选是**可见 transcript 窗口**里的 numbered item / heading / paragraph；
   按指代词与 salience 排序；接受时插入 span 文本。评价指标是 span 的 top-1/top-3 命中。
   §11 的 lexical 基线是 top-3 ≈30%；这是 LLM 臂要跨过的门槛。
5. token 补全保留为第二层，条件仍是“用户确实在打一个 code-shaped token”。

### 10.5 限制

- 60 条、一个用户、一个项目；分层抽样不是总体比例，数字是设计信号。
- “会用”是假设性问题；但它与 `specific` 的 14/14 vs 0/37 分离足够干净，可作为方向证据。
- 引文多是整段/多行；span 解析取最长匹配段落，completion 是其中的次级读数。
- 1 条 `specific`（P55）的引文是表格内容，提取器跳过表格，因此 unresolved。


## 11. 场景修正：引用 chip 才是竞争者（2026-10-25）

§10 的配对口径是「最后一条 assistant 回复」，而真实场景是：**先滚到感兴趣的段落，
再在编辑框写意见**；要引用时，当前最方便的是选中文本 → 弹 chip → 点 chip。
§10 的数字不能用来判死键盘路径——候选池取错了。新增两个离线探针：

- `viewport-probe.mts` → `VIEWPORT-RESULT.json`：引用段落的来源分布；
- `retrieval-probe.mts` → `RETRIEVAL-RESULT.json`：从“意见草稿”能否找回被引用的段落。

### 11.1 引用从哪来（21 天，3,497 个真人回合）

| 读数 | 值 |
|---|---|
| 含 ≥20 字符逐字段落的回合 | **506 / 3,497（14.5%）** |
| 来源是 assistant / user | 400 / 106 |
| 来源是**最后一条 assistant** | **287（56.7%）** |
| 来源早于最后一条 assistant | **219（43.3%）** |
| 来源在最近 3 条消息内 | 393（77.7%） |
| 引用段落长度 p50 / p90 | **39 / 143 字符** |
| 来源距离 p50 / p90 | 1 / 7 条消息 |
| 带指代词但没有逐字引用 | 931（26.6%） |
| 引用回合同时带指代词 | 366 / 506 |

结论：

1. **“最后一条 assistant 回复”作为候选池会漏掉 43% 的引用**，其中 22% 来自 3 条消息之前；
   21% 的引用源是用户自己的消息。候选池必须是**可见 transcript 窗口**，不是最后一条回复。
2. **引用长度中位 39 字符、p90 143**——这不是 token 提一下，而是整段插入。
   键盘路径要产出的也是“插入这段”，不是补全一个词。
3. **14.5% 的回合有逐字引用**（chip 或手工复制的上界），这是 incumbent 的真实体量；
   键盘路径是在这个体量里竞争，不是在 6.9% 的 token 提及时里竞争。
4. 26.6% 的回合带指代词但没有逐字引用；这是键盘路径的语义候选空间，但包含大量普通对话，
   需要严格的触发与精度门槛。

### 11.2 从“意见草稿”找段落：lexical 基线很弱

把引用段从 user 消息里去掉，剩下的就是“意见草稿”；候选是最近 3/5/12 条消息里的段落。

| 候选窗口 | 可评估回合 | top-1 | top-3 |
|---|---:|---:|---:|
| 最近 3 条 | 390 | 15.6% | 26.4% |
| 最近 5 条 | 390 | 15.4% | 29.0% |
| 最近 12 条 | 390 | 15.4% | 30.3% |
| 近处（≤3 条） | 296 | 20.6% | 34.8% |
| 远处（>3 条） | 94 | 0%（3 条池） | 36.2%（12 条池） |

- 506 个引用回合里，79 个（15.6%）是“只引用、没有意见”——这类应继续用 chip；
  427 个（84.4%）带意见，才是键盘路径的候选。
- 意见草稿通常很短（「按你的建议，推进。」「讨论该问题原因，并建议解决方案。」），
  与被引用段落几乎没有词面重叠。**字面匹配不是这个场景的解法。**
- 远处引用在 3 条窗口里 0% 是必然的（源不在池里）；12 条窗口把它拉回 36%，
  但代价是候选变多、精度不变。

### 11.3 三个方案的竞争关系

| 方案 | 精度 | 成本 | 适用 |
|---|---|---|---|
| 选中 → quote chip（ incumbent） | 100%（显式） | 鼠标/手指选择 + 点击 | 所有引用；尤其长段落、跨消息 |
| 键盘前缀补全（reference targets） | 自动回放 top-1 79%，误报 2.1% | 打字 + Tab | 只适合**重打** code token；不覆盖 43% 的远端引用 |
| 停顿 → LLM 选段落 | 未知，需实验 | 一次小模型调用 + 等待 | 写意见时“知道我说的是哪段”，不离开键盘 |

结论：**键盘路径不是“更快的 chip”，而是“不选文本也能指到”的替代路径**。
它的门槛不是击键数，而是**错误插入的代价**：chip 的精度是 100%，键盘路径一旦插错，
用户要撤销、重选，体验比直接选择更差。所以精度优先、短列表、可撤销、绝不自动插入。

### 11.4 下一步实验（不再接线）

1. **LLM 臂的离线回放**：在 390 个“引用 + 意见”回合上，用便宜模型给候选段落排序。
   输入 = 意见草稿 + 可见窗口的段落列表（带 id）；输出 = top-3 + confidence。
   与 lexical 基线（top-3 30.3%）比；目标 top-3 ≥70%、top-1 ≥50%。
2. **假阳性校准**：在 2,991 个无引用回合上跑同一触发，取“召回 70% 时误报 ≤5%”的阈值；
   触发条件：停顿 ≥800ms、草稿 ≥8 字、无 IME、无浮层、lexical 预筛有 ≥2 个候选。
3. **成本/延迟**：记录每次调用的 token、费用、p50/p95 延迟；预算建议 <¥0.01/次、
   p95 <800ms。超过就不做 LLM 臂，回到 chip。
4. **人工标注（40 条引用 + 意见）**：把三臂的 top-3 候选盲排，标“哪段是我想指的 /
   都不是”，再问“你会用它替代选中吗”。这是唯一能测“竞争 chip”的偏好读数。
5. **隐私**：LLM 臂会把**未发送的草稿**和可见 transcript 发给模型。这与现有的
   “发送后才进模型”不同，必须先决定是否接受；可选本地模型、或只在显式触发时发送。

### 11.5 限制

- 逐字引用是 chip 使用的上界：无法区分 chip、手工复制、以及用户重复自己上一句。
- 候选窗口 capped 12 条；更远的引用被漏掉，所以 43.3% 是“至少这么多”。
- 草稿重建只去掉最长的一段引用；多个引用、编辑过的引用会污染草稿。
- 段落切分是启发式的，表格被跳过；ground truth 是“包含被引用 run 的段落”，
  用户可能想指的是整条消息。
- 一个用户、一个项目、21 天；数字是设计信号，不是总体估计。
