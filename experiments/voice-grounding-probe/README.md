# voice-grounding-probe（2026-10-24，小规模探针，不是评测）

目的：给「语音 → 视觉闭环」的快路径做两次初步验证。闭环的含义是：边说边在屏幕上高亮被指到的对象。

- **`probe.py`**：用 kokoro TTS（sid 3）合成 20 条「指向」语句，交给 SenseVoice int8（CPU，4 线程）识别，再在可见候选集上做闭集匹配。可见候选集有两种：fleet 视图有 5 个项目，board 视图有 4 个在途任务。比较三种匹配器：子串精确匹配、去掉非字母数字字符后的 rapidfuzz 模糊匹配、拼音加 rapidfuzz。
- **`pseudo_stream.py`**：SenseVoice 不是流式模型。这里每隔 160 ms 对「到目前为止的音频」重新解码一次，看部分结果能不能逐词跟上。

运行：`/data/home/yale/work/sv-probe/v/bin/python3 -I probe.py`。依赖 pypinyin 和 rapidfuzz，装在 `/tmp/vgp/py`，脚本里通过 `sys.path` 引入。

## 读数

| 项 | 结果 |
|---|---|
| ASR 延迟（整句 0.7–1.5 s 音频） | 中位数 38 ms |
| 子串精确匹配 / 模糊匹配 / 拼音模糊匹配 | 5/20、14/20、11/20 |
| 匹配本身的耗时 | < 0.3 ms |
| 伪流式：4.5 s 的句子每 160 ms 重解一次 | 每步 19–75 ms，随前缀线性增长 |
| 伪流式：词出现在部分结果里的时刻 | 词说完后约 1–2 个步长，也就是 160–320 ms |

## 观察

1. **瓶颈在 ASR，不在匹配。**序号（「第三个」）全部正确。项目名和任务名错得厉害，例如 `claudecodeui → "Can record the cold youy"`、`archguard → "我 god"`、`quay → "嘿/hele"`、`handshake → "Conhenship"`。
2. **部分错误来自 TTS 本身。**这个音色读英文专名并不准，所以合成数据会高估 ASR 在真人语音上的错误率。真人语音要用本机已有的录音（`~/.cloudcli/voice-data` 等）来验证。
3. **模糊匹配的命中里有一部分是碰巧。**比如 `"L那个"` 命中了 locator，阈值 60 偏松。真要用，需要加校准过的置信度，并在不确定时问一轮。
4. **拼音模糊匹配比纯字母模糊匹配差**（11 对 14）。原因是专名本身是英文，ASR 输出却混着中文音译，把它们都转成拼音反而把距离拉大了。
5. **伪流式在 CPU 上就能满足逐词反馈的预算。**但部分结果会抖动（`打开 ↔ 大开`），开头还会冒出日文假名（因为 `language=auto`），所以需要去抖，并固定语言。

## 结论（只是初步）

快路径的匹配和延迟都不是问题，问题集中在**专名的识别**。有两个方向值得做：
- 一是在声学层面让识别器知道候选集，比如热词或受约束的解码，这需要换一个支持这些功能的流式模型；
- 二是不先转写，直接对「音频 × 候选」打分，也就是联合嵌入的路线。
