## 背景

2026-11-21 对运行中会话的高 CPU 做了端到端调查，发现的问题不是单个 spinner，而是**结构规模、合成层、持续动画、背景模糊、首包体积**共同作用：

- 运行中会话页面：172 个 compositor layers（91 draw content），其中 154 个是 276x52 的侧栏项目行；160 个层的提升原因是 `Overlap`。侧栏实际渲染 587 个项目，只有 1 个展开，但有 1,172 个 `sticky top-0 z-10` 元素（`SidebarProjectItem.tsx:250` 与 `:438`）。把 586 个收起项目的 sticky/z-index 临时改成 static 后，层数 **172 → 21**。
- 运行中会话的持续动画：60fps 两只 spinner 实测 total 20.4% / GPU 9.5%（单核口径）；5Hz steps 9.2% / 3.1% 但视觉卡；15Hz steps 14.7% / 4.5%，用户接受。`Shimmer` 已从 `background-position + bg-clip-text`（≈60 次/秒 style recalc）改为 opacity pulse（5–13 次/秒）。
- 背景模糊：侧栏已改为空层 + 有运行会话时关闭；composer/header 仍有常驻 `backdrop-blur` 覆盖流式内容，尚未隔离测量。
- 首包：主 chunk 约 4,551KB（gzip 1,350KB）；`App.tsx` 路由组件全是静态 import，没有 route-level `React.lazy`。
- Transcript 本身已经有 100ms 合并、settled/pending 拆分 + memo、初始 100 条 + LazyMessageRow/IntersectionObserver、`contain + content-visibility`；它不是本轮的主要问题，不应重写。

本仓库此前没有前端性能 ADR。上述原则需要成为后续评审、任务立案和回归判据的共同依据。

## 决策

### 1. 结构优先：先减少 DOM/层/数据规模，再微调单个动画

- 项目列表、transcript、任何可能达到数百行的列表必须有**有界渲染**（虚拟化、分页、只渲染展开/选中项，或明确的“显示全部”）。
- `position: sticky` / `z-index` 只加在需要固定且在滚动的元素上；收起/无会话的项目行不得 sticky。新增 sticky 必须在评审中说明它为什么不会产生 Overlap 层爆炸。
- 侧栏等大列表的收起项默认不渲染 sessions；项目列表默认有界，搜索命中不得被预算遮蔽。
- 层不是免费的：任何新增 `will-change`、`backdrop-filter`、`filter`、`transform`、`position: fixed`、`sticky` 都要问“它是否会让层数上升”，并在固定 workspace 上复测层数。

### 2. 动画策略：持续动画必须 compositor-only、有限帧率、条件化

- 持续动画只允许动 `transform` / `opacity`（compositor-only）；禁止动 layout/paint 属性。
- 对于常驻的小指示器（spinner、pulse、shimmer）：
  - 默认不跑 60fps；使用有限步进（当前侧栏 spinner 为 `steps(15, end)`）或条件化到“仅运行时/仅可见时”。
  - 优先把旋转加在 **wrapper** 上，SVG 本体保持静止（`rendering-animate-svg-wrapper`；浏览器对 SVG 本体的 CSS transform 不保证硬件加速）。
  - 不用 GIF/WebP 替代 CSS 动画：已实测 5fps GIF/WebP total 11.0–11.2%，不比 CSS steps 好，且带来二进制资源、主题配色、GIF 1-bit 透明/调色板问题。
- 一次性入场/退场动画可以保留 `will-change`，但必须在动画结束后不再常驻；禁止 blanket `will-change`。
- 隐藏标签页/不可见区域不得继续跑无意义的持续动画/时钟；轮询必须 visibility-aware。

### 3. 背景模糊：只用在静态背景上，内容在下方变化时条件关闭

- `backdrop-filter` 会在下方帧变化时重算；把它放在流式 transcript/滚动内容上方是高风险形状。
- 侧栏已采用“空背景层 + 有运行会话时关闭 blur”的方案；composer/header 必须先做 A/B 隔离测量，再决定不透明背景、静态背景层或流式期间条件关闭。
- 不得未测量就删除视觉模糊；也不得为了保留模糊而让每帧重算。

### 4. 流式/React：保留已有优化，先 profile 再改

- 保留并保护：100ms 流式合并、`StreamingMarkdown` 的 settled/pending 拆分 + memo、初始 100 条 + 分页、LazyMessageRow/IntersectionObserver、`contain + content-visibility`、拆分 Context + external store 的窄订阅。
- 新增性能改动必须先在固定场景（running + 流式 + >=100 条消息）取得 commit/render/TaskDuration 读数；没有读数的“加 memo/拆 hook”不算优化。
- 不在渲染热路径做布局读写循环；行高/滚动条估算必须按新增/变化行增量或缓存，不能每次流式更新遍历所有可见行。
- 大 hook/大组件（`useChatSessionState`、`useSessionStore`、`ChatComposer`、`ChatInterface`、`CockpitPage`、`ArchitecturePanel`）先 profile 再拆；拆的时候保持状态边界，不把状态提升到更大的 context。

### 5. 加载/资产：路由级拆分、重依赖按需、独立预算

- 不常驻的路由（cockpit、standalone architecture、OAuth consent、settings/code-editor 入口）使用 `React.lazy` + **局部** `Suspense`；不要用全局 Suspense 包住整个 App。
- Markdown 路径中的 Mermaid/KaTeX/语法高亮按需 import；不得让重库进入更多 eager 路径。
- 首包体积是独立轴：不得用“运行中 CPU 降低了”来替代 bundle 读数；也不得为了拆包破坏首屏/状态连续性。
- 目标：主 chunk gzip 在路由拆分后至少下降 20%，并在固定构建上记录 raw/gzip chunk 列表；最终的 bundle 预算按实测校准，不先写死一个拍脑袋数字。

### 6. 测量方法：固定场景、CDP 读数、中位数、A/B

性能结论必须来自可重复测量，而不是单次观察：

- **场景矩阵**：冷启动、空 workspace、100+ 项目/1 展开、running（Thinking 无文本）、流式输出、320 条 transcript + 加载全部、手机 390×844、隐藏标签页、重连、cockpit/architecture/editor。
- **读数**：页级 CDP `Performance.getMetrics`（TaskDuration / ScriptDuration / RecalcStyleCount）、浏览器级 `SystemInfo.getProcessInfo` 按 type 求 CPU 时间差、`LayerTree` 层数与提升原因、`PerformanceObserver` longtask/event/layout-shift、React Profiler、JSHeap/DOM 节点数。
- **协议**：warmup；至少 3–5 个窗口；报中位数 + 原始窗口；记录 viewport、fixture、宿主 load；任何改动做 A/B；headless SwiftShader 的 GPU 绝对值不外推，主线程/层数/相对差更可移植；明确区分“单核百分比”和“整机百分比”。
- 对“先 profile 再改”的任务，允许 no-change 结论，但必须有读数；不得用代码推断代替测量。

### 7. 预算与治理：性能是 ratchet，不是一次性优化

初始预算（在固定 fixture 上校准；可随实测调整，但不得静默放宽）：

- 标准 workspace 的 compositor layers：目标 ≤50（当前 172；P0 单点目标 ≤30）。
- running session 10s 中位：total ≤15% of one core、GPU ≤5%（当前 15Hz 在测量宿主上的水平；真实 GPU 需复测校准）。
- 持续动画：只允许有明确理由的有限集合；新增常驻 60fps 动画必须给出测量理由。
- 标准 workspace DOM 节点：目标 ≤10k（当前 14.7k）。
- 隐藏标签页 10 分钟：CPU 接近 0。
- 首包主 chunk：路由拆分后按实测设定，之后只能下降或说明 recorded change。

每个性能任务必须有：固定场景、fixture、A/B、原始读数、回归判据；性能相关 AC 不得只写“应该更快”。评审清单至少问：是否新增持续动画？是否新增 sticky/层/模糊？是否让 eager bundle 变大？是否在热路径读布局/全量 map？

## 明确不做

- 不重写 transcript 的流式/懒加载架构；它是本仓库已正确实现的部分。
- 不给所有组件加 `memo`/`useMemo`/`useCallback` 或 `will-change`；这些都有成本，必须由 profile 驱动。
- 不用 GIF/WebP/APNG 替代 CSS spinner（已测不更优）。
- 不为“视觉平滑”无条件恢复 60fps；必须以层数/CPU 预算为前提。
- 不把“首包/加载”与“运行中 CPU”混成同一个任务或同一个 AC。
- 不在未测量的情况下移除视觉模糊、sticky 或动画。

## 影响

- 后续前端性能任务按本 ADR 的场景/读数/预算执行；P0/P1/P2 任务已经立案：
  - P0：`gap-sidebar-collapsed-project-sticky-layer-explosion`、`gap-sidebar-project-list-render-budget`
  - P1：`gap-running-spinner-60fps-after-layer-fix`、`gap-composer-header-backdrop-blur-streaming`
  - P2：`gap-frontend-route-level-code-split`、`gap-transcript-pixel-estimate-hotspot`、`gap-hidden-tab-timer-raf-audit`、`gap-chat-hot-path-render-profile`
- 现有 architecture ratchet（oversize / moduleMutableState / hookStateHeavy / providerNameBranches / smallHelperCopies）继续有效；本 ADR 增加的是**运行时/层/加载**维度，不替代代码结构棘轮。
- 后续如果引入性能预算测试，应作为独立任务/门，不在本 ADR 中假装已经落地。
