# 上下文窗口 K 对指代/术语质量的影响：历史 C2 包的锚点位置分析

日期：2026-10-23。数据：`experiments/voice-omni-vs-realtime/out/fixtures-24.json`（24 条真实 utterance 的精确 C2 包）与 `out/results-30c.jsonl`（N0 无上下文 / N1 全上下文，2 reps）。复跑：`python3 experiments/voice-omni-vs-realtime/analyze-context-k.py`。

## 一句话

**在这批历史数据里，K=3 行或约 700 字符就已经达到全上下文的术语命中上限（4/5）；再往下，唯一的失分点是 `711e54cc-0` 的 `live voice`（3 行 / 648 字符）。** 全上下文也修不了的 `pack → 派克` 不是 K 的问题，需要术语级护栏。保守设置是 **4 行 / 1,200 字符**，能保留所有观测到的 Latin/数字锚点；当前 2,000 字符预算有 1.7–2.9 倍余量。

## 一、方法

1. 对 5 个指代/术语 case，在**当时送给模型的完整 C2 包**里找 anchor 的**最后一次出现**，量两个距离：
   - `rows from newest`：从最新一行倒数的行数（1 = 最新一行）；
   - `chars from newest`：从包尾倒数的字符数。
2. 观察 N0（无上下文）/ N1（全上下文）在该 case 上的术语是否命中（`results-30c`，每臂 2 reps）。
3. 做 **necessary-condition** 估计：anchor 还在窗口内 ⇒ 用该 case 的 N1 观测；anchor 丢失 ⇒ 用 N0 观测。这给出“K 至少要多小/多大”的上界，不是一条实测质量曲线。
4. 额外用 24 条里所有**出现在 C2 包中的 Latin/数字 token** 做敏感性检查，避免只看 5 个手工挑的术语。

## 二、锚点位置（精确 C2 包）

| case | anchor | rows from newest | chars from newest |
|---|---|---:|---:|
| `6c76e1cf-0` | `architecture tab` | **1** | 448 |
| `6c76e1cf-0` | `tab` | **1** | 7 |
| `711e54cc-0` | `live voice` | **3** | **648** |
| `acf7fc73-0` | `live voice` | 不在包里 | — |
| `bf517472-0` | `pack` | **1** | 249 |
| `bf517472-1` | `live voice` | **1** | 51 |

- `6c76e1cf-0`：`architecture tab` 在最新一行 448 字符处；`tab` 在最新一行 7 字符处。K=1 行 / 100 字符仍保留 `tab`。
- `711e54cc-0`：`live voice` 在 **3 行 / 648 字符**处，是这批里最深的承重锚点。
- `acf7fc73-0`：包里没有连续 `live voice`，只有分开的 `live` / `voice`（4 行 / 1,114 字符）；但它在 N0 就已经命中，不是上下文依赖 case。
- `bf517472-0`：`pack` 在最新一行 249 字符处；**全上下文仍听成「派克」**，K 无法修。
- `bf517472-1`：`live voice` 在最新一行 51 字符处，最浅。

## 三、N0 / N1 观测

| case | N0（无上下文） | N1（全上下文） |
|---|---|---|
| `6c76e1cf-0` | ✗ / ✗ | ✓ / ✓ |
| `711e54cc-0` | ✗ / ✗ | ✓ / ✓ |
| `acf7fc73-0` | ✓ / ✓ | ✓ / ✓ |
| `bf517472-0` | ✗ / ✗ | ✗ / ✗ |
| `bf517472-1` | ✗ / ✗ | ✓ / ✓ |

- N0 合计 **1/5**，N1 合计 **4/5**（两 rep 一致）。
- 上下文真正的贡献集中在 3 个 case：`6c76`（tab）、`711`（live voice）、`bf517-1`（live voice）。
- `acf7` 是 N0 就能命中的非上下文 case；`bf517-0` 是全上下文也失败的非 K 问题。

## 四、K 曲线（necessary-condition 估计）

| K 行 / K 字符 | 行口径期望命中 | 字符口径期望命中 |
|---:|---:|---:|
| 0 / 0 | 1/5 | 1/5 |
| 1 / 200 | 3/5 | 3/5 |
| 2 / 300 | 3/5 | 3/5 |
| 3 / 500 | 4/5 | 3/5 |
| 3 / 600 | 4/5 | 3/5 |
| 4 / 700 | 4/5 | 4/5 |
| 4 / 800 | 4/5 | 4/5 |
| 6 / 1,000 | 4/5 | 4/5 |
| 10 / 1,200 | 4/5 | 4/5 |
| 12 / 2,000 | 4/5 | 4/5 |

读法：

- **K=0 → 1/5**：没有上下文时，只有本来就不依赖上下文的 `acf7` 命中。
- **K=1–2 行 / ≤600 字符 → 3/5**：`6c76`、`bf517-1` 保住，`711` 的 `live voice` 丢了（它在 3 行 / 648 字符处），模型退回 N0 的「网络测试」。
- **K=3 行 / ≥700 字符 → 4/5**：达到全上下文上限；`bf517-0` 的 `pack` 仍是唯一的 miss，且它不是 K 能修的。
- **行口径与字符口径的差异**：行口径在 K=3 就到 4/5，字符口径要 K=700 才到；原因是一个“行”可能很长（`711` 的第 7 行 648 字符），行数不等于信息量。实际实现如果按字符预算，**700 字符是临界点**；如果按行数，**3 行是临界点**。

## 五、更广的 Latin/数字锚点敏感性

24 条里有 7 条的 C2 包包含至少一个来自 `relay` 文本的 Latin/数字锚点：

| case | anchors | rows from newest | chars from newest |
|---|---|---:|---:|
| `262537d7-2` | Live, Voice | 1 | 231 |
| `529f93f4-0` | Live, live, voice | 4 | 890 |
| `6c76e1cf-0` | architecture, tab | 1 | 448 |
| `711e54cc-0` | live, voice | 1 | 547 |
| `acf7fc73-0` | live, voice | 4 | 1,114 |
| `bf517472-0` | pack | 1 | 249 |
| `bf517472-1` | Live, Voice | 1 | 51 |

- 保留**所有**锚点：行数 p50/p90/max = **1/4/4**；字符 p50/p90/max = **448/1,114/1,114**。
- 行口径：K=1–3 保留 5/7；**K=4 保留 7/7**。
- 字符口径：K=600 保留 5/7；K=1,000 保留 6/7；**K=1,200 保留 7/7**。
- 这比 5 个手工术语更保守：`acf7` 的 `live`/`voice` 分开出现，位置在 4 行 / 1,114 字符；它在 N0 已命中，所以不影响术语结论，但说明“700 字符”不是对所有锚点都安全。

## 六、结论与建议

1. **如果只保 5 个手工指代/术语 case**：K=3 行或 **700 字符**就达到全上下文上限 4/5；K=600 会丢 `711` 的 `live voice`，掉到 3/5。
2. **如果保所有观测到的 Latin/数字锚点**：用 **4 行 / 1,200 字符**。这是保守设置，也是当前 2,000 字符预算下最安全的第一步缩容（省约 40% 上下文）。
3. **不要再往下压到 500 字符以下**：`6c76` 的 448 字符和 `bf517-0` 的 249 字符还在里面，但 `711` 的 648 字符已经丢了；再低会连 `6c76` 都丢。
4. **`pack` 是 K 修不了的**：全上下文仍 `pack → 派克`。需要 term-level 候选/逐字护栏，不能指望加窗口。
5. **当前实现是字符预算**（`VOICE_CONTEXT_BUDGET_CHARS = 2000`，`buildVoiceContextPack` 从最新行向前装到装不下为止），不是行数 K。最小改动是把 `budgetChars` 降到 1,200（保守）或 700（激进）；行数 K 需要新参数，收益不明显。
6. **上线前要一次 live A/B**：700 / 1,200 / 2,000 三档，同一批真实音频，测术语命中、CER、用户编辑率。本记录只证明“锚点在不在窗口内”，不证明“模型一定用得一样好”。

## 七、K=4 / 1,200 的费用影响（估算）

### 包大小

把 24 条真实 C2 包按“最新 4 行、最多 1,200 字符”重切：

| 指标 | 旧（2,000 字符预算） | 新（4 行 / 1,200） |
|---|---:|---:|
| 平均字符 | **1,822** | **873** |
| 中位字符 | 1,877 | 749 |
| 平均行数 | ~9 | **3.5** |
| 字符削减 | — | **949（52.1%）** |

### 费用模型

- 实时模型每次 response 重读整个上下文（F1）；包的 token 按混合会话 ≈ **0.5–0.7 token/字符** 折算。
- 旧包 ≈ 911–1,275 token；新包 ≈ 437–611 token；每次 response 省 **475–665 token**。
- 最近 7 天实时日志：每次 response 文本输入 ≈ **2,052 token**；文本输入占实时费用 **80.5%**。
- 因此实时费用削减 ≈ `(475–665) / 2,052 × 80.5%` = **18.6%–26.1%**，中心约 **22%**。
- one-shot omni：旧 prompt 1,305 token（音频 39 + 文本 1,267，输出 11.7）；新 prompt ≈ 744–827，输出不变；每条约 **¥0.001076 → ¥0.00063–0.00069**，削减 **36%–42%**，中心约 **39%**。
- 合计：实时占当前语音花费的 ~99%，所以总费用削减 ≈ **20%–22%**。

| 路径 | 费用削减 | 绝对量（最近 7 天） |
|---|---:|---:|
| Live voice（realtime） | **~19%–26%**，中心 ~22% | ¥0.356/天 → ~¥0.28/天，省 ~¥0.08/天 |
| Voice input（one-shot omni） | **~36%–42%**，中心 ~39% | 目前 <¥0.05/天，省几分钱 |
| **合计** | **~20%–22%** | 12 天 ¥5.00 → ~¥3.9，省 ~¥1.1 |

### 会让估算偏低的因素

- 长工具会话里，每次 response 的文本输入由工具结果/历史主导，包占比更小；实时削减可能只有 **10%–15%**。
- 如果缩短上下文导致重说/编辑增加，净节省会进一步缩小。
- `buildVoiceInputContextPack` 的草稿/已说块也可能占预算；本估算只按会话包 4 行算，实际 voice input 的削减可能略低。
- 账单以阿里云为准；这里是按仓库单价常量的估算。

## 八、局限

- 5 个手工指代/术语 case、24 条真实 utterance；只报方向，不做显著性。
- 静态 necessary-condition 分析，不是 K 变化的实测输出；模型可能使用 anchor 之外的上下文（解释、话题、邻近句），这些没有被 token 覆盖量捕捉。
- 只分析 Latin/数字锚点；中文指代（「那个」「上面这段」）无法用字符串覆盖来量。
- N0/N1 来自 `qwen3.8-omni-flash` 的 relay 臂；不外推到其他模型。
- C2 包本身已按 2,000 字符截断；这里量的是“在已截断包内再截 K”，不是完整会话历史的 K。
- 只测了 `live voice` / `architecture tab` / `pack` 这几类术语；其他领域术语的锚点深度可能不同。
