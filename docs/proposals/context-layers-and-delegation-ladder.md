# 上下文分层与委托阶梯：让系统持续接手开发者的工作

状态：已获用户认可（2026-10-24）。本文是驾驶舱（cockpit）之后的整体方向，后续任务以它为依据。
来源：「人类 I/O 带宽与 UI 设计原则」会话里关于驾驶舱、语音指示、聚焦和上下文的讨论，以及 `experiments/voice-grounding-probe/` 里的几个小探针。

## 1. 出发点

1. **人的 I/O 和注意力是固定的瓶颈。**开发者大致已经处在能力上限附近；系统才刚开始建设，它的能力边界远在现在能估计的范围之外。长期能增长的只有一个量：**系统接手了多少人的工作。**
2. **人的输入大部分可以被覆盖。**回复建议上线后的第一个小时里，14 条消息有 6 条（43%）直接来自 chip，被采纳的几乎都是决策类回复（取舍、合并、批准）。自己打字的那 8 条，集中在「发起新方向」（3 条）和「问系统是怎么工作的」（3 条）。
3. **驾驶舱需要高频展示的信息很少**：待决策事项及建议选项、自己发起的事做到哪一步、线上实际在跑什么、会话之间的协作。要追求的是这几样始终准确、位置固定、不用读字就能判断，而不是多展示。
4. **做到这些要靠持续积累的上下文。**这里说的上下文不只是一个对话窗口，而是人和系统之间几种相互的理解。

## 2. 四层上下文

| 层 | 谁理解谁 | 内容 | 寿命 | 现状与缺口 |
|---|---|---|---|---|
| L1 工作上下文 | 当下的共同指涉 | 焦点、屏幕可见对象、最近一条回复里的条目、托盘、视图历史 | 秒到分钟 | `quay://` 地址、视图契约、驾驶舱中枢已经落地；回复条目还不能寻址（任务 `chat-reply-items-addressable`） |
| L2 项目约定 | 双方共有 | 约定和决策，例如配置文件优先、封装成类、缓存不过期、测试走 workers 的 LLM 网关 | 周到月 | 散落在各项目的 agent 记忆和 `~/.claude/shared-lessons/` 里；agent 能读，人看不到；同一条纠正反复出现 |
| L3 系统自述 | 人理解系统 | 系统的真实状态（合入、构建、线上运行），以及机制怎么运作（chip 何时生成、是否走缓存、点击后会发生什么） | 实时 | 高频提问由此而来：「检查进展」「接线可用了吗」「chip 什么时候生成」；:3001 缺少 fleet CLI 配置导致的静默失效也属于这一层 |
| L4 开发者模型 | 系统理解人 | 工作流回路、决策风格、通道习惯、注意力节奏、反复出现的纠正 | 周，随时间衰减 | 系统完全没有利用；探针显示构建 / 重启占全部话语的 10%，回路清晰可见 |

四层之间的关系：L1 是每次交互的地基；L2、L4 从大量交互中沉淀出来，L4 里反复出现的纠正会升格为 L2 的约定；L3 是 L4 增长时的平衡力，系统接手得越多，人越需要看清它在替自己做什么。

## 3. 证据（小探针，仅作方向参考）

- **指代来源**：从 1003 条真实短句里抽 40 条人工标注，指向对话上文的 15 条、需要检索的 8 条、屏幕上可见的 6 条、没有指代的 10 条。
- **言语行为**：查询 14、讨论 10、指令 8、报告「我做了什么」6、控制 / 确认 2。查询的「方面」约 7 个枚举就能覆盖 10/14。
- **习惯回路**：在 116 个会话、1982 条话语上粗分类后统计转移，主回路是：立任务 →（19%）检查进展 →（30%）构建 / 重启 →（31%）再次构建 / 重启 或 落地核验；浏览器验证 →（17%）立任务。
- **语音快路径**：本机 SenseVoice 识别中位延迟 38 ms；伪流式每 160 ms 重解一次即可做到逐词反馈；瓶颈在专名识别，不在匹配算法。

## 4. 整体方案

```
                 ┌──────────── 统一交互事件流（主机级，本机）────────────┐
  话语 / chip 显示与采纳 / 焦点与指代 / 任务流转 / 构建与重启 / 纠正 / 预测
                 └──────────────────┬──────────────────────────────────┘
         ┌──────────────────────────┼────────────────────────────┐
   共享上下文账本               影子预测器                    系统自述
 （L2 约定 + L4 习惯，     （L4：预测下一步，记录预测与实际）  （L3：流转链、部署就绪、
   带证据，可确认可修改）                                       机制说明）
         └──────────────┬───────────┴────────────────┬───────────┘
               委托阶梯（按操作类别分级）                驾驶舱 / 会话呈现
```

### 4.1 统一事件流：唯一的事实来源

各层都从事件流派生，不再各自去读转写、日志和任务库。事件包括：每条话语（带粗分类）、chip 的显示 / 采纳 / 重抽、驾驶舱的焦点和指代解析结果、发送的预览 / 确认 / 取消、任务状态变化、合入、构建、重启，以及作为一等事件的**纠正**（系统给出了什么，人改成了什么）和**预测**（影子预测的内容与结果）。

存储放在主机级，由 quay-fleet 负责（`~/.quay-fleet/context/`，具体格式与 fleet 对齐后写入任务）。CloudCLI 写交互类事件，fleet 写流转类事件。

### 4.2 两个账本：可见、可改

- **约定账本（L2）**：初始来源是各项目记忆、`~/.claude/shared-lessons/`，以及反复出现的纠正。每一条都注明来源，分为 proposed / confirmed / retired 三种状态。生成 chip、撰写任务、做评审时都以它为依据。
- **习惯账本（L4）**：只描述「你通常怎么做」，不当作规则。每条附次数和例子，随时间衰减，可以否认或删除。习惯首先被当作「能不能交给系统做」的候选。

### 4.3 委托阶梯：主线

每一类操作都处在下面某一级：

```
你自己做 → 系统预测（不显示，只记录）→ 系统建议（chip / 默认焦点）→ 系统做、你确认 → 系统自动做（可查、可撤回）
```

- **晋级靠证据**：影子预测持续命中，且置信度校准得当 → 系统提出晋级 → **由人批准**。人推翻一次，就记一次降级证据。
- **每晋一级都要配上 L3**：本周系统替你做了什么、每一次的记录和理由、一键退回。
- 当前位置：决策类回复在「系统建议」级；构建 / 重启、检查进展在「你自己做」级；发起新方向和价值判断留在人手里。

### 4.4 人的角色

人的输出集中在三件事：**发起**（新方向、新问题）、**判断**（取舍、品味）、**校准**（纠正系统）。校准是系统能力增长的燃料，所以纠正必须做到极其便宜，并且被结构化地记录下来。

### 4.5 呈现原则

- 驾驶舱只常驻四样高频信息，并且都以「系统的提议，你批不批」的形式呈现。
- 界面要按「系统做了什么、你是否批准」来设计，这样它会随系统能力一起扩展；按「你要做什么」来设计的界面，会被人的能力上限卡住。

## 5. 度量

| 指标 | 含义 | 当前 |
|---|---|---|
| 单位进展消耗的人类操作数 | 总目标，应持续下降 | 待建（依赖事件流） |
| 各类操作在阶梯上的分布 | 应持续上移 | 见 4.3 |
| chip 采纳率 / 差一点就对的比例 | L4 预测的质量 | 43%（1 小时，14 条） |
| 影子预测命中率（按类别） | 实测系统的能力边界 | 粗分类的回路统计，单步约 20–30% |
| 同一纠正的复发次数 | L2 是否生效；复发说明账本失效 | 待建 |

## 6. 分工

- **CloudCLI**：记录交互类事件；负责账本与阶梯的呈现和编辑；驾驶舱与会话视图；构建与重启（`scripts/restart-server-detached.sh`、`/health` 的 buildSha、`scripts/check-deploy-freshness.mjs`）。
- **quay-fleet**：主机级存储与 schema（唯一来源）、读口、流转类事件；账本跨项目存放。

## 7. 路线

| 阶段 | 内容 |
|---|---|
| P0 | 地址空间、驾驶舱、中枢、回复建议、回复条目可寻址（大部分已落地） |
| **P1 地基** | 统一事件流写入 + 影子预测器 + 按类别的命中率表 |
| **P2 第一次晋级** | 「构建 + 重启」升到「系统做、你确认」：部署就绪状态（N 个变更待生效 · 构建状态）→ 一键构建 + 安全重启（需确认）→ 重启后自动核验；同时上线任务流转链状态 |
| P3 账本只读 | 约定账本、习惯账本带证据展示；chip 自解释（来源、时间、是否缓存、点击行为） |
| P4 纠正一等化 | 结构化记录纠正；账本可编辑；账本接入 chip 与任务生成；统计纠正复发 |
| P5 阶梯通用化 | 任意类别都可凭证据提出晋级，由人批准；每周汇报「系统替你做了什么」 |

## 8. 守则

1. 习惯是描述，不是规范：先作为自动化候选，不固化成规则。
2. 一切可见、可改、可撤回：两个账本、阶梯级别、每一次自动行为都是如此。
3. 晋级要有证据，并由人批准；不能静默接手。
4. 防止自我强化：chip 始终保留一个「不同方向」的选项；偏离习惯本身也是信号。
5. 习惯和预测随时间衰减。
6. L4 只留在本机，不经任何上报路径离开主机。
