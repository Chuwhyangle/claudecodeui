状态：Draft / 待评审

关系：

## 已确认的决策

| # | 决策 | 含义 |
|---|---|---|
| D1 | **不限制单次使用时长** | 一次 Live Voice 开一小时是正常使用。成本保护只允许是**速率**保护，不得因连接总时长或总额而结束会话（`VOICE_REALTIME_MAX_CNY_PER_CONNECTION` 仅作显式开关，默认关闭）。 |
| D2 | **费用标准**：账单中单行 > ¥0.01 视为异常 | 一次连接结束记一行，所以「单次连接成本」是被盯着的量；异常必须能被日志和告警在几秒内看到。 |
| D3 | 保留**收尾一句**（工具结果之后模型回一句 `OK`） | 实测去掉它后，后续话语 5 句里有 3 句被听到却没有转发（见 F7）。本方案不以它换省钱。 |
| D4 | 模型**不回答、不评论、不整理**，只转发 | 与现状一致；上下文只用于修正识别（标识符、同音词），不是让模型去理解会话。 |

## 目标

1. **成本与连接时长无关**：每句话的成本为常数，不随对话变长而上升。目标 ≤ ¥0.0035 / 句，在 69 句/小时的说话频率下 ≤ ¥0.25 / 小时。
2. **只把语音发给上游**：在 CloudCLI 一侧做 VAD，缓冲并合并相隔很短的语音，较长间隔才提交；无语音的片段不发送。
3. **一次说话 = 一次提交**：把被停顿切碎的片段在发给模型之前合并，消除上游 VAD 把一句话切成多段（含识别为空的段）。
4. **固定大小的文本上下文**：每次响应读到的文本是一个有上限的包（指令 + 工具 + 上下文包），不随响应次数增长。
5. **长连接可持续**：空闲时透明换一个新的上游会话，丢弃不再需要的历史，浏览器一侧不感知。
6. **每一步可观测、可对账**：每个片段、每次响应、每次换会话都有日志与用量，能与阿里云账单逐位对上。

## 非目标

- 不更换模型；不改变中继语义；不让语音模型回答问题或读取会话后自行决策（它没有读会话的工具，见 D4）。
- 不做 TTS（语音回复）。
- 不在 V1 做「用模型生成会话摘要」（会话摘要生成本身要花 token，作为后续项）。
- 不改 Claude Code 一侧的任何行为；不计入 Claude Code 自己处理消息的 token。
- 不改变现有的合并窗口（2.5 秒）与忙等待投递逻辑；它们保留，作为兜底。

所有数字来自 2026-10-09/10 的线上日志、录下的真实会话（`server/modules/voice-realtime/tests/fixtures/`）和阿里云账单；「推断」一栏明示。

| # | 事实 | 数据 | 来源 |
|---|---|---|---|

| F3 | 音频输入按 **7 token/秒**，不足 1 秒按 1 秒 | 「输入音频计算公式为 总 Tokens 数 = 音频时长（单位：秒）* 7」 | [百炼 Qwen-Omni 文档](https://help.aliyun.com/zh/model-studio/user-guide/qwen-omni)（Qwen3.8-Omni-Flash 一节；realtime 页面只给价格表） |
| F4 | 静音没有被计费 | 浏览器送了 10,250 帧 = 205 秒，账单音频 token 只有 546；若 205 秒新增音频都计费，最少 1,435 | **推断**（与 F3 对账），文档只说「累计媒体时长不是会话总时长」 |
| F5 | 提交给模型的语音只是送出的一小部分 | VAD 窗口合计 8.56 秒（含边缘约 14–16 秒），占 205 秒的约 4–8% | 日志 `speech_started`/`speech_stopped` |
| F6 | 实时模型按**连接**结束汇总记一行 | 账单 07:43 那一行 = 该连接的总数（6,360 / 146 逐位吻合） | 账单 + 日志对账 |
| F7 | 去掉「收尾一句」会漏转发 | 去掉后 5 句里 3 句只回文字 `No response requested.`，从未调用 `session_send` | 2026-10-10 测试实例日志 |
| F8 | 工具结果措辞可造成循环 | 结果写「will be delivered when the user stops speaking」后，模型每 0.65 秒重试一次：89 次调用、300,121 输入 token、≈ ¥0.49 / 分钟 | 日志 + 账单 07:09 |
| F9 | 上游服务端 VAD 会把一句话切碎 | 3 段语料产生 13 条转发消息；加了 CloudCLI 合并后降为 5 条；一句话被切成两个窗口，其中一个转写为空串 | HTTP 诊断 |
| F10 | 上游连接时间与稳定性波动大 | 连接建立 0.2–9 秒；约 1/10 的连接在 `speech_started` 后不再回事件 | HTTP 诊断 20+ 次 |
| F11 | 平台自己会丢弃过旧的历史 | 「音频历史最多 100 轮、累计 600 秒；较早历史在超过轮数或累计媒体时长时被丢弃」 | [qwen3.8-omni-flash-realtime 页面](https://alibabacloud.com/help/en/model-studio/qwen3-8-omni-flash-realtime) |
| F12 | 单价（元 / 千 token） | 文本输入 0.0015，音频输入 0.006，文本输出 0.0045 | 账单 |

**由此得出的成本结构**：音频几乎不花钱（每句约 ¥0.00025）；钱花在「文本输入 × 响应次数」。降低成本的杠杆是：**每次响应读到的文本上限**，以及**不让它随时长增长**。

## C1 浏览器端切分（SegmentVAD）

### 输入输出

- 输入：`audioSource` 产出的 `VoiceRealtimeAudioFrame`（20 ms，Float32，已有，见 `src/modules/chat/voice-realtime/audioSource.ts`）。
- 输出：一串**语音段**，每段是 16 kHz 单声道 PCM16，附序号 `seq`、起止时间、时长。

### 参数（默认值，均可配置；数值需在验收中标定）

| 参数 | 默认 | 含义 |
|---|---|---|
| `frameMs` | 20 | 判定粒度 |
| `startFrames` | 3（60 ms） | 连续这么多帧超过进入阈值才判为开始说话 |
| `preRollMs` | 300 | 段首向前回溯，避免吃掉起音 |
| `hangoverMs` | 700 | 低于退出阈值后保持这么久才算「这次停顿」 |
| `mergeGapMs` | 1,500 | 两段语音之间的静默短于此值就**合并成一段**（把句内停顿接上） |
| `commitGapMs` | 2,000 | 静默达到此值才提交这一段（略大于 `mergeGapMs`，给合并留出判定窗口） |
| `maxSegmentMs` | 20,000 | 一段的上限；到达时在最近的能量低点处强制切开 |
| `minSegmentMs` | 250 | 短于此的段视为噪声丢弃（不发送） |
| 阈值 | 自适应 | 进入/退出阈值相对噪声基线（沿用 `src/shared/voiceTrim.ts` 的 3.0 / 1.8 倍基线，基线取**滑动窗口**第 15 百分位，而不是整段） |

### 状态机

```
IDLE ──(startFrames 连续高能量)──► SPEAKING(段首 = 当前 − preRollMs)
SPEAKING ──(低能量持续 hangoverMs)──► PAUSED(记录 pauseStart)
PAUSED ──(静默 < mergeGapMs 内再次开口)──► SPEAKING   （合并：同一段继续，间隙里的静默**保留**为短静音）
PAUSED ──(静默 ≥ commitGapMs)──► COMMIT：封口，输出一个语音段 ──► IDLE
SPEAKING ──(时长 ≥ maxSegmentMs)──► 在最近低能量点 COMMIT 并立即开始下一段
```

- 合并时间隙里的静音**保留**（不拼接掉），让下游模型看到真实的停顿，也不改变语速。
- 连接断开 / 用户点 End / 静音（Mute）：已缓冲未提交的段**先提交**再处理（End 与静音都不得丢掉最后一句话）。

### 协议

浏览器 → 服务端新增帧（旧的连续 `audio` 帧继续兼容，走原有「上游服务端 VAD」路径，便于灰度）：

| 帧 | 字段 | 说明 |
|---|---|---|
| `segment_start` | `seq`, `startedAtMs` | 一个语音段开始 |
| `audio` | `audio`(base64 PCM16), `seq` | 段内的帧；带 `seq` 的 `audio` 属于该段 |
| `segment_end` | `seq`, `durationMs`, `reason`(`gap`/`max`/`end`) | 段结束，服务端据此提交 |

服务端 → 浏览器新增：

| 帧 | 字段 | 说明 |
|---|---|---|
| `segment_ack` | `seq`, `state`(`committed`/`dropped`), `reason?` | 段已提交给模型，或被丢弃（过短、上游不可用） |
| `rotated` | `reason`, `ms` | 信息性：上游会话已换（不需要用户操作） |

### 提交方式（需 P0 验证）

在 CloudCLI 做了切分后，上游应关闭自己的 VAD：`session.update` 里 `turn_detection: null`（手动模式），服务端在 `segment_end` 时依次发 `input_audio_buffer.commit`、`response.create`。**此前我们只在文本回合里验证过 `turn_detection: null`，音频手动提交没有验证过**，这是 P0 的第一项（见「分期」）。若手动模式不可用，回退方案：保持服务端 VAD，但只在段内持续送帧、段与段之间送**不超过 `commitGapMs` 的真实静音**，让上游自己的 VAD 与我们的边界基本一致。

## C2 上下文包（ContextPack）

### 目的与边界

上下文包**只用于让语音识别 / 转发更准**（把「voice点se」纠成 `voice.service.ts`，把同音词纠成会话里出现过的词），**不是让模型理解会话**：D4 规定模型仍然不回答、不改写、不推理。

### 预算

| 项 | 默认 | 说明 |
|---|---|---|
| `contextBudgetTokens` | **1,000** | 上下文包本身的文本 token 上限 |
| 固定指令 + 工具 | 约 450 | 现状，不计入包 |
| 每次响应读入的文本合计 | ≈ 1,450 | 指令 + 工具 + 包 |
| 低配档 `lean` | 500 | 只放标识符表；用于对成本最敏感的场景 |

包的组装是**服务端的确定性函数**，不经过任何模型，所以不额外花 token。

### 内容（按优先级截断，截断后保证 ≤ 预算）

1. **会话标识**（≤ 60 token）：会话标题、项目名。
2. **标识符表**（≤ 400 token）：近期会话里出现的文件名、函数 / 类 / 变量名、命令、模块名；按近期性与频次排序；每个只出现一次。
3. **近期用户消息**（≤ 300 token）：最近 N 条（含已转发的语音消息）的原文，各自截断。
4. **近期助手回复要点**（≤ 240 token）：最近一次回复的首尾片段（确定性截取，不做摘要）。

### 数据来源与隐私（硬约束）

- 来源：服务端已有的会话读取服务（与 `session_get` 同源，经 `server/modules/voice-realtime/` 的执行器依赖注入，不新增对其它模块的深度导入）。
- **隐私**：包会发给第三方模型。默认**只发「会话标识 + 标识符表」**，不发消息原文；发送近期消息原文需要用户在设置里**显式开启**，并有脱敏规则（路径中的家目录、形如密钥 / token 的字符串、`.env` 内容一律剔除）。这一项不得默认开启。
- 包的内容与大小在日志中记录哈希与 token 数，不记录原文。

### 估算

token 数没有现成的本地分词器时，用「CJK 字符 ≈ 1 token、其余按空白与标点 ≈ 4 字符 / token」估计，并用每次响应返回的 `usage.input_tokens` **在线校准**（记录估计值与实测值之差，超过 20% 告警）。

## C3 上游会话池与换会话（UpstreamPool）

### 为什么换会话

F1：同一会话里每次响应的读入每次多约 75 token。20 句话（40 次响应）累计约 8 万 token。对中继而言这些历史没有价值（模型不需要记得 5 分钟前转发了什么）。换一个新会话即可把读入重置回「指令 + 工具 + 包」。

### 为什么不是「每句一个新会话」

F10：连接建立 0.2–9 秒不等，每句都新连会引入用户可感的延迟与失败面。因此：**预热待命会话 + 空闲时切换**。

### 规则

| 项 | 规则 |
|---|---|
| 触发 | 上一次响应的 `usage.input_tokens` 超过 `rotateAtTokens`（默认 `contextBudgetTokens + 450 + 600`，约 2,000），或会话已服务 `rotateAfterSegments` 段（默认 12） |
| 预热 | 触发阈值的 70% 时在后台新建待命会话，完成 `session.update`（指令 + 工具 + 最新上下文包） |
| 切换时机 | **仅当**：没有未提交的段、上一个响应已 `response.done`、距最近一次语音 ≥ `idleBeforeSwitchMs`（默认 1,500）。切换是把后续的段发往待命会话，随后关闭旧会话 |
| 说话中到达阈值 | 不切换；继续用旧会话直到下一个空闲点；若上游平台自行丢弃历史（F11）也不影响正确性 |
| 切换失败 | 待命会话建立失败或已断开：保留活动会话，记 `ROTATE_FAILED`，下一个空闲点重试；不得中断用户的语音 |
| 无状态假设 | 切换不迁移任何模型历史；新会话只带指令 + 工具 + 当前上下文包 |

### 与现有重连的关系

- 现有 bridge 的「上游意外断开 → 自动重连并重新声明」保留，且复用同一个 `session.update` 构造函数（带包）。
- 一个**已提交但未收到 `response.done`** 的段，在会话切换或重连后按 `seq` 幂等重放一次（见 AC-9）。

## C4 / C5 沿用与扩展

- **投递（C4）**：2.5 秒合并窗口、会话忙时等待并并入同一条、`session_send` 单飞保护全部保留。C1 合并之后，合并窗口主要处理「模型把一个段拆成两次调用」的情况。
- **循环保险**：两次完整语音之间工具调用超过 6 次，桥不再回应（`TOOL_LOOP_GUARD`）；工具结果文案固定为「已接受，不要再调用，回复 OK」。
- **速率保护（C5）**：30 秒内估算花费超过 ¥0.015 结束连接（`SPEND_LIMIT`），不设总额上限（D1）。
- **新增日志**（每段一行，带时间戳）：`segment seq=… dur=…ms merged=… reason=… sent=…frames`、`response in=… out=… cost~CNY…`、`rotate reason=… from=… to=… idle=…ms`、`pack tokens=… est=… hash=…`。

## 成本模型

### 变量

| 符号 | 含义 | 取值 |
|---|---|---|
| `C` | 每次响应的文本读入 | 1,000（含指令与工具）/ 1,450（指令与工具之外另加 1,000 的包） |
| `r` | 每句话的响应次数 | 2（转发 + 收尾 OK） |
| `a` | 每句语音秒数 | 3.0（均值 2.14 秒 + 边缘；合并短间隙取 3） |
| `o` | 每句输出 token | 36（实测 146 / 4） |
| `u` | 说话频率 | 69 句 / 小时（4 句 / 208 秒）；120 句 / 小时（4 句 / 120 秒的说话区间） |

### 公式

```
每句成本 = r·C·0.0015/1000 + r·max(1,a)·7·0.006/1000 + o·0.0045/1000
```

### 结果

| C | 每句 | 69 句 / 小时 | 120 句 / 小时 |
|---|---|---|---|
| 1,000 | ¥0.0034 | **¥0.24** | ¥0.41 |
| 1,450 | ¥0.0048 | ¥0.33 | ¥0.57 |
| （对比）现状 | 随长度上升 | 约 ¥1.1–1.4 | 约 ¥2.3–3.7 |

### 预算（验收口径）

- 每句 p50 ≤ ¥0.005；
- 69 句 / 小时 ≤ ¥0.35；
- 单次响应读入（文本）≤ `C` + 音频（≤ 60 token）。

## 失败模式与降级

| 失败 | 处理 |
|---|---|
| 手动提交不被上游支持 | 回退到「服务端 VAD + 段间只送短静音」；功能开关 `VOICE_REALTIME_MODE=continuous` 保持旧路径 |
| 浏览器 VAD 漏检（小声说话） | 自适应阈值 + 在 UI 的麦克风指示上给出电平；`minSegmentMs` 之外不丢段；日志计数 `vad.missedSuspect`（有字幕却无段，仅在连续模式下可见） |
| 一句话被 `maxSegmentMs` 强切 | 在能量低点切；两段的转发消息由 C4 合并 |
| 待命会话建立失败 / 变慢 | 保留活动会话，不影响说话；告警 |
| 上下文包过期（用户刚切了话题） | 包只含标识符表与近期消息，错用的代价是纠错偏差而非转发错误；包在每次换会话时重算，且**每个新话题的第一句不依赖包** |
| 上游中途断开 | 已提交未完成的段按 `seq` 重放一次；仍失败则 `segment_ack dropped` 并告知用户 |
| 费用异常 | 沿用速率保护；日志逐段记账，可与账单逐位对上 |

## 安全与隐私

- 上下文包**默认不含消息原文**；含原文需显式开启，且经脱敏（见 C2）。
- 不改变密钥持有方式：DashScope 密钥只在服务端。
- 诊断接口默认 dry-run 不变；`--live` 仍需显式。
- 日志不记录包的内容与语音内容，只记录 token 数、哈希、时长与序号。

## 开放问题

1. **手动提交是否支持**（P0-S1）。决定 C1 的整体形态。
2. **平台对「文本历史」的丢弃规则**：文档只说明音频历史与轮数上限（F11）；函数调用、工具结果、`OK` 这类文本是否同样受 100 轮约束没有说明，需实测。
3. **`conversation.item.delete` 是否支持**：若支持，可以不换会话而是删除旧条目，省去预热会话；P0 顺带验证。
4. **标识符表的来源**：从会话 transcript 抽取的规则（正则 + 去重）能否覆盖中文口述里的「点」「杠」等读法，需要与 `voice-identifier-repair-and-temporal-compression.md` 的修复规则合并设计，避免两处各修一遍。
5. **上下文包要不要放近期消息原文**（隐私 / 成本 / 效果三者的权衡）：本 SPEC 默认不放；是否开放给用户选择，待评审。
6. **多设备 / 多标签同时使用 Live Voice**：同一会话的两个浏览器连接各自持有上游会话，成本翻倍；是否限制为一个活动语音连接，待评审。

## 范围外的相关项（另行跟进）

- 实验脚本（`experiments/`）没有任何 token 上限；2026-10-04 的大额消耗来自那里，不是本链路。建议加「本次最多 N token」开关。
- 诊断接口的调用频率限制与 `--allow-spend`。
